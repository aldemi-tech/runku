## Data model and lifecycle result

- `ctx.db.query(table, options?)` is one typed contract for physical table paging, logical ordered
  indexes, word-search indexes, and bounded fallback scans. Omitted options select a 100-document
  page in stable `$createdAt DESC, $id DESC` keyset order; the public maximum is 200.
- Arbitrary unindexed filters and sorts inspect at most 2,000 documents before returning
  `DATA_QUERY_REQUIRES_INDEX`. Equality prefixes, ordered suffixes, and `gt`/`gte`/`lt`/`lte`
  bounds select and narrow matching ordered indexes. `contains` remains a bounded substring/array
  fallback; `search` requires a declared whole-word index.
- Tables default to `queryable`; `keyValue` restricts them to point access and writes. Both modes
  retain one canonical document representation. Moving from `keyValue` to `queryable` registers
  projections and performs bounded, idempotent, resumable backfill before the Release is servable.
- Building and active Release catalogs participate in dual writes. Compatible older Release
  views preserve unknown fields on replace, so concurrent Releases can use additive schema views
  over the same records. Version 0.5.3 intentionally does not garbage-collect retired index rows.
- Function declarations now require only `handler`; authentication, visibility, capabilities,
  arguments, and return contracts have stable safe defaults. New string bounds count Unicode code
  points through `minLength`/`maxLength`; byte bounds remain exclusive to `v.bytes` while legacy
  persisted string-byte contracts remain decodable.

## Database result

- SQLite schema versions 3 and 4 add the physical document scan and durable index registry.
- PostgreSQL schema versions 4 through 6 add the same scan/registry plus a durable database mode.
  `dedicated` is the default and binds an empty database atomically to one exact Environment;
  `shared` is explicit and retains Project/Environment scope in every logical key.
- A real PostgreSQL 16 container passed common store conformance, concurrent OCC, repeatable-read
  snapshots, bounded pool health, Query, Mutation, dedicated Product binding, restart, and
  Management readiness checks. The concurrent first-binding campaign exposed a bootstrap race;
  bounded portable migration retry was added and the complete Product campaign then passed.
- A real single-node YugabyteDB YSQL `2026.1.1.1-b2` container passed the common logical-store
  contract plus Query and Mutation execution. The exact image used was
  `yugabytedb/yugabyte@sha256:3926eedf0ff4b99426fbff533128ff16635ed5697a5cf086dde4fafec28e6f75`.
  This proves adapter compatibility, not RF=3 failure tolerance, performance, backup/restore RPO,
  or multi-node production qualification.

## Known boundaries

- Runku still admits one active application writer per Environment. Distributed SQL does not make
  Product serving, Realtime dispatch, or scheduling active-active.
- Shared database mode is logical multitenancy, not per-Environment role isolation. Operators must
  bound pools, credentials, placement, noisy neighbors, backup, and restore for the shared tier.
- Search is normalized case-insensitive whole-word lookup with at most 4,096 distinct words per
  document. It does not provide phrase search, stemming, substring search, relevance ranking, or
  arbitrary secondary sorts.
- Applying the additive PostgreSQL/SQLite migrations makes binary downgrade unsupported. Take and
  verify a coordinated backup before upgrading.
- The local Yugabyte campaign used RF=1. Production Yugabyte requires a separately reviewed
  multi-node topology, RF/failure-domain evidence, monitoring, backup, restore, and measured load.
